\begin{abstract}
Emergency coordinators and volunteer groups in Innlandet must follow official flood, landslide and weather warnings that are published by two agencies, in different formats, and revised several times a week. Today the active warnings for the county are collected by hand and retyped into briefings. We propose a small agentic harness that fetches the warnings from the NVE and MET Norway open APIs, lets a language model write a short plain-Norwegian summary of each warning, and assembles a daily digest whose factual content is checked by code before anyone reads it. The central design choice is that the model writes prose only: warning identifiers, danger levels, areas and dates are copied deterministically from the source, and a checker rejects any digest that drops, duplicates, alters or invents a warning. This report describes the problem, a binary definition of success, the architecture, a schedule to the demonstration, and the main risks.
\end{abstract}

\section{Problem}

\textbf{Recurring need.} Innlandet is Norway's largest county by area, with river systems such as Glomma, Gudbrandsdalslågen and Mjøsa, and a mountain interior. Flood and landslide warnings from the Norwegian Water Resources and Energy Directorate (NVE) and weather warnings from MET Norway are therefore issued for the county repeatedly every autumn and spring. Municipal emergency coordinators (\emph{beredskapskoordinatorer}) and volunteer organisations such as the Red Cross, Norwegian People's Aid and local search-and-rescue teams need an up-to-date picture of which warnings apply to their area, at which level, and for which period. Today that picture is assembled manually by checking varsom.no and MET's warning pages and copying the relevant warnings into an email or briefing note. The work is repetitive, it has no single owner, and its failure modes are costly: a missed update, a cancelled warning still being circulated, or a wrong danger level.

\textbf{What the workflow produces.} Once a day, the harness produces \code{out/digest.json} and a readable \code{out/digest.md}. Each entry contains the official warning identifier, type, danger level, affected area and validity period, copied from the source, plus a summary of at most 60 words in plain Norwegian written by the agent. The digest carries the attribution required by the data licences and links to varsom.no. A person reads the digest and decides whether and how to pass it on; the system never sends messages.

\textbf{Users and constraints.} Users are described by role only. The workflow processes public, official warnings and stores no personal data. Both sources are open: NVE data is licensed under NLOD~2.0 and MET Norway data under NLOD~2.0 and CC~BY~4.0, both requiring attribution. We follow MET's terms (identifying \code{User-Agent}, caching) and NVE's request not to selectively remove parts of a warning: the official fields are always kept intact, and the agent's text is labelled as our summary.

\section{Definition of success}

A run is successful if and only if \code{python eval/check\_digest.py} exits with code~0. The checker compares the digest with the raw source response saved in \code{fixtures/} for that run and enforces the following binary properties:

\begin{enumerate}
  \item \textbf{Completeness:} every active warning for Innlandet in the source (danger level~$\geq 2$, valid in the period) appears in the digest exactly once, identified by its source ID.
  \item \textbf{No invention:} every \code{warning\_id} in the digest exists in the source.
  \item \textbf{Fidelity:} for each warning, \code{danger\_level}, \code{valid\_from} and \code{valid\_to} are equal to the source values.
  \item \textbf{Locality:} every warning in the digest lists Innlandet (county number~34) among its counties.
  \item \textbf{Grounded summaries:} every date, time and number that appears in a \code{summary\_no} also appears in the source record for that warning, and each summary is at most 60 words.
  \item \textbf{Attribution and privacy:} the digest contains the NVE and MET attribution strings and no e-mail addresses or phone numbers (regular-expression check).
  \item \textbf{Empty case:} if the source contains no active warning, the digest states this explicitly and contains no warnings.
\end{enumerate}

Properties 1--7 are mechanically decidable. Whether a summary is \emph{useful} and \emph{readable} is not; for the final evaluation we will add a documented LLM-as-judge rubric for these qualities, reported separately from the binary checks.

\textbf{Stage 1: Fetch (tool use).} \code{harness/fetch.py} calls the NVE flood-warning API (\url{https://api01.nve.no/hydrology/forecast/flood/v1.0.10}), endpoint \url{/api/Warning/County/34/1/{start}/{end}}, with an identifying \code{User-Agent}. Landslide warnings and MET MetAlerts (\url{metalerts/2.0/current} with \code{county=34}, \code{geographicDomain=land}) are added after the skeleton. The raw response is written to \code{fixtures/}, and \code{-{}-offline} replays a saved fixture, so every run is reproducible without network access.

\textbf{Stage 2: Normalise.} The raw records are mapped to one schema (\code{source}, \code{warning\_id}, \code{type}, \code{danger\_level}, \code{area}, \code{valid\_from}, \code{valid\_to}, official text fields) and filtered to warnings that list county~34 and have level~$\geq 2$. This list is the single source of truth for all facts in the digest.

\textbf{Stage 3: Summarise (agent step).} One call to a local model, \code{llama3.2:3b} served by Ollama, receives the normalised list and a context file, \code{prompts/digest.md}, which defines the audience, the plain-language rules, the meaning of the NVE activity levels and the required JSON output (\code{warning\_id} $\rightarrow$ \code{summary\_no}). The model sees only the normalised warnings for Innlandet, not the raw API dump or other counties, which keeps the context small and limits the surface for instructions embedded in warning text. Official text is passed inside clearly delimited data blocks, and the prompt states that it is data, not instructions.

Without an API key, or with \code{-{}-no-llm}, the stage falls back to deterministic template summaries built from the official fields, and \code{-{}-offline} replays a saved model answer from \code{fixtures/}, so the full pipeline is reproducible without network or key. Running the model locally keeps the cost of a run at zero and the warning data on our own machine. The daily GitHub Actions run has no local model, so it uses the template fallback; the summaries written by the model come from local runs.

\textbf{Stage 4: Assemble.} \code{harness/assemble.py} joins the model's summaries to the Stage~2 records by \code{warning\_id} and writes \code{out/digest.json} and \code{out/digest.md} with attribution. The model's output is never trusted for facts; a summary for an unknown ID is discarded and a missing summary fails the check.

\textbf{Stage 5: Check.} \code{eval/check\_digest.py} implements the properties of Section~2. The check was committed before the code it tests and is protected from the coding agent by a \code{deny} rule on \code{Edit(/eval/**)} in \code{.claude/settings.json}.

\textbf{Automation.} \code{python harness/run.py} runs Stages 1--5 with one command. A GitHub Actions workflow runs it on a daily cron schedule, stores the digest as a build artifact, and fails visibly when the check fails. The API key is held as a GitHub secret and in a git-ignored \code{.env} locally. A kill switch stops the run without a digest if the API fails, the model returns invalid JSON, or more than 60 active warnings appear; \code{run.py} deletes stale output first so an old digest cannot fake a pass. Publication remains a human decision: the digest is never sent anywhere automatically.

\textbf{Development context.} \code{CLAUDE.md} tells the coding agent how to run the checks and states the rules (no edits to \code{eval/}, no personal data). Each unit of work is specified in \code{tasks/NNN-*.md} with an acceptance check, implemented on a branch, and merged through a reviewed pull request; corrections of agent output are recorded in \code{docs/prompt-log.md}. Task~001 (a probe of MET Norway's forecast API) has been completed this way and established the fixture and \code{-{}-offline} pattern reused here.

LLM changes a level or date, or invents a warning & Facts never pass through the model (Figure~\ref{fig:arch}); property~5 rejects ungrounded numbers in summaries; a failed check means no digest. \\
Prompt injection in warning text & Warning text is passed as delimited data; output must match a fixed JSON schema; tested as an input perturbation in week~46. \\
API change, outage or rate limiting & Version-pinned endpoint (NVE keeps old versions for at least six months), fixtures and \code{-{}-offline}, explicit error on non-200 responses instead of a partial digest. \\
Cost, key or data leakage & The summary model runs locally through Ollama, so a run costs nothing and warning data stays on our machine; no API key is needed, and any optional key lives only in \code{.env} (git-ignored, read-denied for the coding agent) or GitHub secrets; one model call per run with a fixed output token limit. \\
Weaker Norwegian from a small local model & \code{llama3.2:3b} is a small model and may write less fluent or less plain Norwegian than a large hosted model. The binary checks still protect the facts; the quality of the language will be measured in the evaluation with the readability rubric. \\
Time: two people, five weeks & Thin end-to-end skeleton first; sources are added one task at a time; MetAlerts is dropped before the evaluation work if time runs short. \\

\section{Prompt log (excerpts)}

The full log is in \code{docs/prompt-log.md}. The following entries show agent output that we corrected or rejected.

\begin{itemize}[leftmargin=1.2em]
  \item \textbf{2026-10-01, task 001 plan: missing contact in the User-Agent.} The agent's plan for the MET Norway probe used a default \code{User-Agent} without contact information, which MET's terms of service require. We rejected the plan and had the agent use the repository URL instead: \code{weather-demo-live/0.1 github.com/zetsukko/weather-demo-live}. The code passed the check either way; only reading the plan caught the problem.
  \item \textbf{2026-10-01, unrequested push.} While scaffolding the repository, the agent pushed to GitHub without being asked. We now review \code{/diff} before every commit and push ourselves.
  \item \textbf{2026-10-01, credential in the git remote.} The agent noticed a GitHub token embedded in the \code{origin} remote URL and printed it in the session. We revoked the token and switched to credential-manager login. This confirmed the need to keep secrets out of anything the agent can read or print.
  \item \textbf{2026-10-26, specification contradicted the assignment.} The agent-drafted \code{SPEC.md} listed scheduling as out of scope, although the technical minimum requires an automatic part. We moved the daily run into scope and kept only hosting and notifications out.
  \item \textbf{2026-10-26, wrong licence.} The same draft gave MET Norway's licence as CC~BY~4.0 only; MET's licence page states NLOD~2.0 and CC~BY~4.0. Corrected after checking the source.
  \item \textbf{2026-10-26, facts kept away from the model.} Rather than accept a design where the model writes the whole digest, we required that identifiers, levels, areas and dates are copied by code and that the check rejects any number in a summary that is not in the source.
\end{itemize}
